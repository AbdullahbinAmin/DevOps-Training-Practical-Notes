# Chapter 13: Kubeadm — Setup, Installation & Cluster Creation

**What is kubeadm?** A tool used for the more "real-world"/bare-metal style of building a Kubernetes cluster: you take 2 or more actual servers, run kubeadm on one to make it the **master**, and then **join** the other servers as **workers**. Unlike KIND/Minikube (single machine, simulated), this uses genuinely separate machines — closer to how production clusters are built.

**Setup used here:** 2 EC2 instances (t2.medium), named `master-k8s` and `worker-k8s`, same security group, with inbound port **6443** opened (this is the port workers use to join the master).

---

## Commands to run on BOTH master and worker nodes

### 1. Turn off swap memory
```bash
sudo swapoff -a
```
**What it does:** Kubernetes requires swap memory to be disabled on every node. Swap is a technique where the OS uses disk space as "extra RAM" when real RAM is full — Kubernetes doesn't support this well because it can make memory management for containers unpredictable. `-a` means "turn off all swap areas."

### 2. Load required kernel networking modules
```bash
sudo modprobe overlay
sudo modprobe br_netfilter
```
**What it does:** Kubernetes needs special Linux kernel features enabled to let containers talk to each other over the network across different physical/virtual machines.
- `overlay` → a filesystem module containers use.
- `br_netfilter` → lets network bridge traffic be filtered/processed properly, needed for Kubernetes' pod networking to work.
- `modprobe` = "module probe," the Linux command to load a kernel module.

### 3. Configure required sysctl networking parameters
```bash
sudo sysctl --system
```
(usually after writing settings into a config file, e.g. enabling `net.bridge.bridge-nf-call-iptables`)
**What it does:** Applies networking-related kernel settings needed so that traffic passing through Linux network bridges is correctly seen by `iptables` (the firewall/routing rules system) — necessary because now you have multiple separate instances that need to talk to each other, unlike KIND/Minikube where everything sat on one machine.

### 4. Install containerd (the container runtime)
```bash
sudo apt-get update
sudo apt-get install -y containerd
sudo systemctl restart containerd
sudo systemctl status containerd
```
**What it does:**
- `containerd` is an **industry-standard container runtime** (a CNCF graduated project) — the actual engine that runs containers behind the scenes. Even Docker itself uses containerd internally! Here, containerd will be used directly (without full Docker) to run all Kubernetes' internal components (API server, etcd, scheduler, controller-manager on the master; kubelet, kube-proxy on the worker).
- `apt-get install -y containerd` → installs it (`-y` auto-confirms "yes" to any install prompts).
- `systemctl restart containerd` → restarts the containerd service so new settings take effect.
- `systemctl status containerd` → checks whether containerd is "active (running)" — confirms the install worked.

### 5. Install kubeadm, kubelet, and kubectl
```bash
sudo apt-get update
sudo apt-get install -y apt-transport-https ca-certificates curl gpg
curl -fsSL https://pkgs.k8s.io/core:/stable:/v1.29/deb/Release.key | sudo gpg --dearmor -o /etc/apt/keyrings/kubernetes-apt-keyring.gpg
echo 'deb [signed-by=/etc/apt/keyrings/kubernetes-apt-keyring.gpg] https://pkgs.k8s.io/core:/stable:/v1.29/deb/ /' | sudo tee /etc/apt/sources.list.d/kubernetes.list
sudo apt-get update
sudo apt-get install -y kubelet kubeadm kubectl
sudo apt-mark hold kubelet kubeadm kubectl
```
**What each part does, in plain English:**
- `apt-transport-https ca-certificates curl gpg` → basic tools needed so `apt` (Ubuntu's package manager) can safely download packages over HTTPS and verify their authenticity.
- `curl ... | sudo gpg --dearmor -o ...` → downloads Kubernetes' official signing key and saves it so Ubuntu can verify the packages are genuinely from the Kubernetes project (security check).
- `echo 'deb [...]' | sudo tee /etc/apt/sources.list.d/kubernetes.list` → tells Ubuntu's package manager "here's a new source/repository to fetch Kubernetes packages from" (in this case, version 1.29 — you could swap this for 1.32 or any other version by changing the URL).
- `apt-get install -y kubelet kubeadm kubectl` → installs the three core Kubernetes command-line tools:
  - **kubelet** → the agent that runs on every node and makes sure containers/pods are actually running correctly (used mainly on worker nodes).
  - **kubeadm** → the cluster-bootstrapping tool (used to `init` a master or `join` a worker).
  - **kubectl** → the tool you (the human) use to send commands to the cluster.
- `apt-mark hold kubelet kubeadm kubectl` → "locks" these packages at their current version, so a routine `apt-get upgrade` won't accidentally update Kubernetes to a different (possibly incompatible) version.

**Everything above this point (swap off, kernel modules, containerd, kubeadm/kubelet/kubectl) is run identically on BOTH the master and worker instances.**

## Commands to run ONLY on the master node

### 6. Initialize the cluster (this makes THIS server the master)
```bash
sudo kubeadm init
```
**What it does:** Whichever server you run this command on **becomes the master node / control plane**. It installs and starts:
- The **API server** (communication gateway)
- The **scheduler** (decides which node runs new pods)
- The **controller manager** (keeps everything in the desired state)
- **etcd** (the cluster's database)

At the end, it prints out a **join command** (containing a secure token) that you'll copy and run on worker nodes later.

### 7. Set up kubectl access for your regular (non-root) user
```bash
mkdir -p $HOME/.kube
sudo cp -i /etc/kubernetes/admin.conf $HOME/.kube/config
sudo chown $(id -u):$(id -g) $HOME/.kube/config
```
**What it does:** By default, kubeadm's config file (which kubectl needs to talk to the cluster) is only accessible by the `root` user. These 3 commands:
1. `mkdir -p $HOME/.kube` → creates a `.kube` folder in your normal user's home directory.
2. `sudo cp -i /etc/kubernetes/admin.conf $HOME/.kube/config` → copies the admin config file there.
3. `sudo chown $(id -u):$(id -g) $HOME/.kube/config` → changes the file's **ownership** to your own user (instead of root), so you (e.g. the `ubuntu` user) can run `kubectl` commands directly without needing `sudo` every time.

### 8. Install a pod network add-on (Calico)
```bash
kubectl apply -f https://raw.githubusercontent.com/projectcalico/calico/v3.28.0/manifests/calico.yaml
```
**What it does:** Kubeadm sets up the master/worker relationship, but nodes still need a way to talk to each other over the network — that's the job of a **Container Network Interface (CNI)**. Here, **Calico** is used.
- `kubectl apply -f <url>` → tells Kubernetes "read this YAML file (a 'manifest') from this URL and create/apply everything described in it." This installs all of Calico's required resources (Custom Resource Definitions, ClusterRoles, Deployments, etc.) in one shot.

### 9. Check cluster status on the master
```bash
kubectl get nodes
```
At this point, only the master itself will show up in the node list, since no worker has joined yet.

## Commands to run ONLY on worker node(s)

### 10. (Only if needed) Undo a wrong `kubeadm init` on a worker
```bash
sudo kubeadm reset
```
**What it does:** If you accidentally ran `kubeadm init` on what was supposed to be a worker node (turning it into a second master by mistake), `kubeadm reset` undoes/reverts all the changes that `kubeadm init`/`kubeadm join` made, giving you a clean slate to try again correctly.

### 11. Generate a fresh join command (run on the master, if the original one expired/was lost)
```bash
kubeadm token create --print-join-command
```
**What it does:** Creates a new secure token and prints the exact `kubeadm join ...` command (including the master's IP, port 6443, and the token) that a worker node needs to run to join the cluster.

### 12. Join the worker to the cluster
```bash
sudo kubeadm join <master-ip>:6443 --token <token> --discovery-token-ca-cert-hash sha256:<hash>
```
**What it does:** Run this **on the worker node**. It:
- Connects to the master's API server at port `6443` (the port you opened earlier in the security group).
- Uses the **token** to prove it's allowed to join (this is a security measure so random machines can't join your cluster).
- Starts the **kubelet** service on this worker, which will now start receiving instructions from the master.

Output will confirm: **"This node has joined the cluster."**

### 13. Verify the worker joined (run on master)
```bash
kubectl get nodes
```
Now shows 2 nodes: the master (control-plane, Ready) and the worker (initially "NotReady" while it finishes setting up, then "Ready").

### 14. Watch node status update live
```bash
kubectl get nodes --watch
```
**What it does:** `--watch` (or `-w`) keeps the command running and automatically refreshes the output every time something changes — so you can literally watch the worker node flip from "NotReady" to "Ready" in real time without re-running the command manually.

### 15. Quick test: run a sample pod
```bash
kubectl run nginx --image=nginx:latest
```
**What it does:** Creates and runs a single Pod named `nginx` using the official `nginx:latest` Docker image, as a quick smoke-test that the cluster can actually schedule and run workloads. (Pods are explained fully in the next chapter — this is just a sanity check here.)
