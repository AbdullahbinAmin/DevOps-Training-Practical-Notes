# Chapters 30–31: Ingress & Annotations

## Chapter 30: Ingress

**Problem:** You have multiple Services (e.g. an `nginx-service` and a `notes-app-service`). You want a **single entry point** where:
- `/nginx` routes to the nginx service.
- `/app` routes to the notes-app service.

A regular Service can't do this path-based routing across multiple apps — that's the job of **Ingress**.

**What is Ingress?** A Kubernetes resource that manages **traffic routing rules** into the cluster, redirecting requests to different Services based on the URL path (or hostname).

## Step 1: Install an Ingress Controller
Ingress rules do nothing on their own — you need an **Ingress Controller** (the actual software that reads your Ingress rules and performs the routing/reverse-proxying/load-balancing). This example uses the popular **ingress-nginx** controller, specifically configured for KIND clusters (found by searching **"KIND ingress documentation"**, since different Kubernetes setups need slightly different controller configs).

```bash
kubectl apply -f https://raw.githubusercontent.com/kubernetes/ingress-nginx/main/deploy/static/provider/kind/deploy.yaml
```
**What it does:** Applies the official manifest that installs everything needed for the ingress-nginx controller on a KIND cluster.

### Check it installed correctly
```bash
kubectl get ns
kubectl get pods -n ingress-nginx
```
You should see a namespace called `ingress-nginx` was created, containing a completed setup Job and a running controller Pod.

```bash
kubectl get svc -n ingress-nginx
```
Shows the controller's own Service (usually named something like `ingress-nginx-controller`, of type `LoadBalancer` or `NodePort`).

## Step 2: Write an Ingress manifest (ingress.yaml)

```yaml
kind: Ingress
apiVersion: networking.k8s.io/v1
metadata:
  name: nginx-notes-ingress
  namespace: nginx
spec:
  rules:
    - host: tws.example.com
      http:
        paths:
          - path: /nginx
            pathType: Prefix
            backend:
              service:
                name: nginx-service
                port:
                  number: 80
          - path: /app
            pathType: Prefix
            backend:
              service:
                name: notes-app-service
                port:
                  number: 8000
```

**Explanation:**
- `kind: Ingress`, `apiVersion: networking.k8s.io/v1` → Ingress is part of the `networking.k8s.io` API group.
- `spec.rules` → a list of routing rules.
  - `host:` → the domain name this rule applies to (can be any placeholder like `tws.example.com` for local testing).
  - `http.paths` → a list of **path-based routes**:
    - `path: /nginx`, `pathType: Prefix` → **any URL starting with** `/nginx` matches this rule. (`pathType: Prefix` means "match this path and anything after it," as opposed to `Exact`, which would only match that literal path.)
    - `backend.service.name` / `port.number` → which Service (and port) to redirect matching traffic to.
  - A second rule does the same for `/app` → `notes-app-service` on port `8000`.

**Important prerequisite:** all the Services referenced must be in the **same namespace** as each other (and ideally the same namespace as the Ingress) — a common source of errors in this session was having `notes-app`'s Deployment/Service in a different namespace than `nginx`'s, causing routing to fail. Fix by deleting and recreating them all in the same namespace:
```bash
kubectl delete deployment notes-app -n notes-app
kubectl delete service notes-app-service -n notes-app
kubectl delete namespace notes-app
```
Then reapply those same manifests but with `namespace: nginx` instead.

## Step 3: Apply the Ingress
```bash
kubectl apply -f ingress.yaml
```
**Possible validation error:** *"error validating ingress... kind not recognized"* → usually caused by a typo in `kind: Ingress` (capitalization matters in YAML/Kubernetes — `kind` must exactly match).

## Step 4: Expose the Ingress Controller so you can actually reach it
```bash
kubectl port-forward service/ingress-nginx-controller -n ingress-nginx --address 0.0.0.0 8080:80
```
**What it does:** Forwards traffic from your host's port `8080` to the ingress controller's own service, which listens on port `80` and internally handles the path-based routing you configured.
- If port `80` (or `8080`) is already taken (**"bind: address already in use"**), just pick a free port instead (this session ended up using `8080` after `80` conflicted).

Then open port `8080` in your EC2 security group's inbound rules, same as before.

## Step 5: Test in the browser
```
http://<ec2-public-ip>:8080/nginx
http://<ec2-public-ip>:8080/app
```
Each path should route to its respective service.

### Debugging note: trailing slash behavior
A path like `/app` (Django) may show a **"Page Not Found"** error even though it's technically routing correctly — this is because many web frameworks expect requests to either include or exclude a trailing slash consistently (e.g. `/app/` vs `/app`), and mismatches cause the app itself to 404, even though Kubernetes' routing is working fine. This is where **Annotations** (next chapter) help fix such path-rewriting issues.

## Chapter 31: Annotations

**What is an Annotation?** Extra metadata/configuration you attach to a Kubernetes object (in `metadata.annotations`) that isn't a core structural field, but gives special instructions to a specific controller (here, to the ingress-nginx controller specifically) about how to behave.

## Adding a rewrite-target annotation to fix the routing

```yaml
metadata:
  name: nginx-notes-ingress
  namespace: nginx
  annotations:
    nginx.ingress.kubernetes.io/rewrite-target: /
```

**Explanation:**
- `nginx.ingress.kubernetes.io/rewrite-target: /` → tells the **nginx ingress controller specifically** (annotation keys are usually prefixed with the controller's own domain, so it knows this instruction is meant for it): "whenever a request matches one of my path rules (like `/nginx` or `/app`), **strip that prefix and rewrite the request to just `/`** before forwarding it to the backend service." This solves the earlier "Page Not Found" issue, because now the backend app receives a clean `/` request instead of `/app` or `/nginx`, which is what it actually expects.

## Applying the change
```bash
kubectl apply -f ingress.yaml
kubectl port-forward service/ingress-nginx-controller -n ingress-nginx --address 0.0.0.0 8080:80
```
Now visiting `/nginx` correctly shows nginx's welcome page, and `/app` correctly shows the Django app — both properly routed AND properly rewritten.

## Key lesson for students
- **Annotations = extra, controller-specific configuration** that doesn't fit into the "normal" structural spec fields — things like custom timeouts, rewrite rules, or other controller-specific tuning.
- You can search **"nginx ingress annotations"** to find the full list of available annotations (timeouts, SSL settings, custom headers, etc.) — you're not expected to memorize them, just to know they exist and where to look them up.
- Ingress problems are notoriously tricky to debug in real life — practicing with an actual working example (like this one) is much more valuable than just memorizing the theory.
