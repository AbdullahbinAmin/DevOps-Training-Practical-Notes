# Chapter 32: StatefulSets

## Stateless vs Stateful apps
- **Stateless apps** (Django, Flask, Spring Boot web apps, etc.) → don't strictly need to remember anything between requests; if you lose one and a new one starts, it's usually fine. Use **Deployments/ReplicaSets/DaemonSets** for these.
- **Stateful apps** (MySQL, MongoDB, and other databases) → data **must** be reliably persisted, reads/writes must be consistent, and identity really matters. Use **StatefulSets** for these.

## What makes a StatefulSet special?
Unlike a Deployment (where replica pods get random names like `nginx-deployment-x7f2k`), a StatefulSet names its pods **predictably and sequentially**: `mysql-statefulset-0`, `mysql-statefulset-1`, `mysql-statefulset-2`, etc. If pod `-0` is deleted, **the replacement is also named `-0`** and gets reconnected to the same persistent storage that pod `0` had — its "state" carries over.

## Writing a Namespace, headless Service, and StatefulSet for MySQL

### 1. Namespace
```yaml
kind: Namespace
apiVersion: v1
metadata:
  name: mysql
```

### 2. Headless Service (service.yaml)
```yaml
kind: Service
apiVersion: v1
metadata:
  name: mysql-service
  namespace: mysql
spec:
  clusterIP: None
  selector:
    app: mysql
  ports:
    - name: mysql
      port: 3306
      targetPort: 3306
      protocol: TCP
```
**Key detail — `clusterIP: None`:** This makes it a **Headless Service**. Normally a Service gets its own internal cluster IP, but a headless service **doesn't** — it exists purely so other pods can reach each individual pod **directly by name** (e.g. `mysql-statefulset-0.mysql-service`), rather than getting load-balanced randomly to any replica. This matters for databases, where you often need to talk to a *specific* replica (e.g. the primary), not just "any one of them."

### 3. StatefulSet (statefulset.yaml)
```yaml
kind: StatefulSet
apiVersion: apps/v1
metadata:
  name: mysql-statefulset
  namespace: mysql
spec:
  serviceName: mysql-service
  replicas: 3
  selector:
    matchLabels:
      app: mysql
  template:
    metadata:
      labels:
        app: mysql
    spec:
      containers:
        - name: mysql
          image: mysql:8.0
          ports:
            - containerPort: 3306
          env:
            - name: MYSQL_ROOT_PASSWORD
              value: "root"
            - name: MYSQL_DATABASE
              value: "deps"
          volumeMounts:
            - name: mysql-data
              mountPath: /var/lib/mysql
  volumeClaimTemplates:
    - metadata:
        name: mysql-data
      spec:
        accessModes:
          - ReadWriteOnce
        resources:
          requests:
            storage: 1Gi
```

**Explanation of the StatefulSet-specific parts:**
- `spec.serviceName: mysql-service` → **links this StatefulSet to its headless Service** — this is a required field unique to StatefulSets, tying pod identity/DNS to that specific service.
- `spec.replicas: 3` → same idea as Deployment — 3 numbered pods.
- `env:` → **environment variables** passed into the container. MySQL's official image *requires* `MYSQL_ROOT_PASSWORD` to be set (its own startup script demands it) — here set to `"root"`. `MYSQL_DATABASE: "deps"` tells MySQL to auto-create a database named `deps` on first startup.
- `volumeMounts` → same idea as before: attach a volume named `mysql-data` at `/var/lib/mysql` (where MySQL actually stores its data files internally).
- `volumeClaimTemplates` → **this is the big StatefulSet-specific feature.** Instead of creating one shared PVC for all pods, a StatefulSet **automatically creates one unique PVC per replica**, following the same numbering (`mysql-data-mysql-statefulset-0`, `-1`, `-2`...). This is exactly how each numbered pod keeps its **own separate, persistent storage** tied to its specific identity.
  - **Important indentation gotcha (a real error hit in this session):** `volumeClaimTemplates` must sit at the same YAML indentation level as `template`, directly under `spec` — **not nested inside** `template.spec`. Also, the field is spelled `template` (singular) inside `spec.template`, but common typos like writing `templates` (plural) anywhere will cause a decoding error. **Always copy this structure from the official Kubernetes documentation** (search "kubernetes statefulset") rather than trying to memorize it.

## Commands

### 1. Apply everything (service first is fine either way, but namespace always first)
```bash
kubectl apply -f namespace.yaml
kubectl apply -f service.yaml
kubectl apply -f statefulset.yaml
```

### 2. Watch pods get created in strict numerical order
```bash
kubectl get pods -n mysql --watch
```
**What you'll see:** `mysql-statefulset-0` reaches `Running` **before** `mysql-statefulset-1` even starts `ContainerCreating`, which starts before `-2` — strictly sequential, unlike a Deployment where all replicas can start in parallel. Press `Ctrl+C` to exit the `--watch` view.

### 3. Enter a specific numbered pod and use MySQL directly
```bash
kubectl exec -it mysql-statefulset-0 -n mysql -- bash
```
Once inside:
```bash
mysql -u root -p
```
(enter the root password you set, `root`)
```sql
SHOW DATABASES;
```
You should see the `deps` database that was auto-created via the `MYSQL_DATABASE` environment variable — proving your configuration actually took effect.

Exit MySQL and the container:
```bash
exit
exit
```

### 4. Delete a specific pod and watch it come back with the SAME name
```bash
kubectl delete pod mysql-statefulset-0 -n mysql
kubectl get pods -n mysql
```
**What you'll see:** A new pod is created — but it's named `mysql-statefulset-0` again (not some new random name), and it reattaches to the same PVC (`mysql-data-mysql-statefulset-0`) it had before. **This is the defining feature of a StatefulSet**: identity + storage stay tied together across restarts.

### 5. Check the service (confirm no external/cluster IP)
```bash
kubectl get svc -n mysql
```
You'll see `mysql-service` with **no CLUSTER-IP** (shown as `None`) — confirming it's a proper headless service, meant purely for internal pod-to-pod addressing like `mysql-statefulset-0.mysql-service`.

## Key lesson: StatefulSet vs Deployment vs ReplicaSet
| | Deployment | ReplicaSet | StatefulSet |
|---|---|---|---|
| Pod naming | Random suffix | Random suffix | Sequential, stable (`-0`, `-1`, `-2`) |
| Rolling updates | Yes | No | Yes (ordered) |
| Persistent identity + storage per pod | No | No | **Yes** |
| Typical use case | Stateless web apps | Rarely used directly | Databases (MySQL, MongoDB, etc.) |
