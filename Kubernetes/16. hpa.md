# Chapter 38: HPA (Horizontal Pod Autoscaler)

## Concept overview
- **HPA (Horizontal Pod Autoscaler)** → increases/decreases the **number of pod replicas** automatically, based on real-time metrics (like CPU usage). Used for stateless apps (Deployments).
- **VPA (Vertical Pod Autoscaler)** → increases/decreases the **resource limits of a single pod** (giving it "more power," not more copies). Used for stateful apps.
- **KEDA (Kubernetes Event-Driven Autoscaling)** → scales based on external event sources (queue length, etc.) rather than just CPU/memory — mentioned as an advanced/less common alternative.

Autoscaling decisions are based on **metrics** — quantifiable numbers like CPU % and memory usage.

## Step 1: Check if a Metrics Server exists
```bash
kubectl top node
kubectl top pod
```
**What it does:** Shows live CPU/memory usage per node or pod. **Error you'll get if not installed:** *"Metrics API not available."*

## Step 2: Install the Metrics Server
```bash
kubectl apply -f https://github.com/kubernetes-sigs/metrics-server/releases/latest/download/components.yaml
```
**What it does:** Installs the Metrics Server (a Deployment, Service, and RBAC Role in the `kube-system` namespace) that continuously collects CPU/memory usage from every node's kubelet.

### Fix for local/KIND clusters (TLS bypass needed)
On a real cloud cluster (EKS/AKS/GKE) this works out of the box, but on a local KIND cluster without proper HTTPS certs, you need to bypass a security check:
```bash
kubectl -n kube-system edit deployment metrics-server
```
**What it does:** Opens the metrics-server Deployment's YAML live for editing. Inside, under the container's `args`, add:
```yaml
args:
  - --kubelet-insecure-tls
  - --kubelet-preferred-address-types=InternalIP,Hostname,ExternalIP
```
**What this does:** Tells the metrics-server "it's okay to talk to kubelets without verifying HTTPS certificates" — a workaround appropriate for local/learning clusters (never disable TLS verification like this in a real production cluster).

Save the edit (`:wq` in vim), then restart the deployment so it picks up the change:
```bash
kubectl rollout restart deployment metrics-server -n kube-system
```

### Debug: pod stuck Pending after installing metrics-server
```bash
kubectl get pods -n kube-system
kubectl describe pod <metrics-server-pod> -n kube-system
```
**Real gotcha hit in this session:** the metrics-server pod stayed `Pending` — turned out **all worker nodes were still tainted** from the earlier Taints/Tolerations chapter! Fix:
```bash
kubectl taint nodes tws-cluster-worker prod=true:NoSchedule-
kubectl taint nodes tws-cluster-worker2 prod=true:NoSchedule-
kubectl taint nodes tws-cluster-worker3 prod=true:NoSchedule-
```
**Lesson:** Taints from an earlier exercise can silently block completely unrelated pods (like metrics-server) from ever scheduling — always check `kubectl describe pod` if something mysteriously stays Pending.

## Step 3: Confirm metrics now work
```bash
kubectl top node
kubectl top pod -n nginx
```
Now shows actual CPU/memory numbers per node/pod (e.g. control-plane using some %CPU and some MB memory; each worker node's usage; each pod's usage).

### Find/remove the heaviest resource-consuming pod (practical use of `top`)
```bash
kubectl top pod -n nginx
kubectl delete pod <heaviest-pod-name> -n nginx
```
Demonstrates a real practical use: identify which pod is consuming the most resources and act on it.

## Step 4: Build a sample app to autoscale (Apache)
```bash
mkdir apache
cd apache
```

### Namespace
```yaml
kind: Namespace
apiVersion: v1
metadata:
  name: apache
```

### Deployment (apache-deployment.yaml)
```yaml
kind: Deployment
apiVersion: apps/v1
metadata:
  name: apache-deployment
  namespace: apache
spec:
  replicas: 1
  selector:
    matchLabels:
      app: apache
  template:
    metadata:
      labels:
        app: apache
    spec:
      containers:
        - name: apache
          image: httpd:latest
          ports:
            - containerPort: 80
          resources:
            requests:
              cpu: "100m"
              memory: "128Mi"
            limits:
              cpu: "200m"
              memory: "256Mi"
```
**Note:** Apache's actual Docker image name is `httpd` (not literally "apache") — a good example of why you always double-check real image names on Docker Hub.

**Common error:** *"Selector does not match template labels"* → the fix is always to make sure `spec.selector.matchLabels` and `spec.template.metadata.labels` use the **exact same key-value pair** (here `app: apache`).

### Service (apache-service.yaml)
```yaml
kind: Service
apiVersion: v1
metadata:
  name: apache-service
  namespace: apache
spec:
  selector:
    app: apache
  ports:
    - protocol: TCP
      port: 80
      targetPort: 80
  type: ClusterIP
```
**Common error:** *"field selector of type string cannot be unmarshal"* → happens if `selector` is accidentally written nested under `labels` instead of directly under `spec` — Service selectors are a plain key-value map directly under `spec.selector`, not inside a `labels` sub-object.

### Apply everything
```bash
kubectl apply -f namespace.yaml
kubectl apply -f apache-deployment.yaml
kubectl apply -f apache-service.yaml
kubectl get all -n apache
```

### Bonus: internal DNS naming for services (good to know)
```bash
kubectl describe service apache-service -n apache
```
Inside the cluster, any pod can reach this service using the internal DNS name:
```
apache-service.apache.svc.cluster.local
```
(`<service-name>.<namespace>.svc.cluster.local` — this only resolves **from inside** the cluster, not from your laptop's browser.)

### Manually scale first (to see the difference vs auto-scaling)
```bash
kubectl scale deployment apache-deployment -n apache --replicas=3
kubectl get pods -n apache
```
**Key point made in the video:** scaling like this is still **manual** — you looked at traffic and decided to scale it yourself. True auto-scaling means Kubernetes decides and reacts on its own.

## Step 5: Create the actual HPA

```bash
kubectl scale deployment apache-deployment -n apache --replicas=1
```
(scale back down to 1 before testing autoscaling from a clean baseline)

```yaml
kind: HorizontalPodAutoscaler
apiVersion: autoscaling/v2
metadata:
  name: apache-hpa
  namespace: apache
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: apache-deployment
  minReplicas: 1
  maxReplicas: 5
  metrics:
    - type: Resource
      resource:
        name: cpu
        target:
          type: Utilization
          averageUtilization: 5
```

**Explanation:**
- `kind: HorizontalPodAutoscaler`, `apiVersion: autoscaling/v2` → HPA-specific API group.
- `spec.scaleTargetRef` → **which resource to scale**: specifies the `apiVersion`, `kind` (Deployment/ReplicaSet/StatefulSet), and `name` of the target — here, our `apache-deployment`.
- `spec.minReplicas: 1` → never scale below 1 pod.
- `spec.maxReplicas: 5` → never scale above 5 pods, no matter how much traffic hits it.
- `spec.metrics` → the rule for **when** to scale:
  - `type: Resource` → base the decision on a standard resource metric (CPU/memory).
  - `resource.name: cpu` → specifically watch CPU usage.
  - `target.type: Utilization`, `averageUtilization: 5` → **"if average CPU utilization across all replicas reaches 5%, add more replicas."** (5% is set deliberately low here purely to make it easy to trigger during a live demo — a real production value would typically be much higher, e.g. 60-80%.)

```bash
kubectl apply -f hpa.yaml
kubectl get pods -n apache
```
Confirms back down to 1 replica before load testing.

## Step 6: Generate load to trigger autoscaling
```bash
kubectl port-forward service/apache-service -n apache --address 0.0.0.0 8080:80
```
Then open the EC2 security group's inbound rules for that port. To actually generate traffic, an **online stress/load-testing tool** (e.g. a browser-based load generator) was used to repeatedly hit the public URL and drive CPU usage up.

## Step 7: Watch it scale automatically
```bash
kubectl get hpa -n apache
kubectl get pods -n apache --watch
```
**What you'll see:** As load increases, the `TARGETS` column in `kubectl get hpa` shows rising CPU utilization; once it crosses the 5% threshold, new pods automatically appear (up to the max of 5), all **without you running any `scale` command yourself** — this is the difference between manual scaling and true HPA-based auto-scaling.

## Key lesson for students
- **HPA needs a Metrics Server** to function — this is a very common "why isn't my HPA working" root cause.
- HPA scales the **number of replicas**; it does not change a single pod's resource limits (that's VPA's job, next chapter).
- Always double check `kubectl describe pod` if something is unexpectedly `Pending` — as seen here, an unrelated leftover taint from an earlier exercise silently blocked metrics-server for a while.
