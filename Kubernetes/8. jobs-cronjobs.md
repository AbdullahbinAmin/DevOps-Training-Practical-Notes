# Chapters 22–23: Jobs & CronJobs

## Chapter 22: Jobs

**What is a Job?** Unlike a Deployment (which keeps a container running forever, like a web server), a **Job** runs a container to do **one task, once, and then stop**. Examples: taking a backup, applying a patch, running a one-time script.

## Writing a Job manifest (job.yaml)

```bash
vim job.yaml
```
```yaml
kind: Job
apiVersion: batch/v1
metadata:
  name: demo-job
  namespace: nginx
spec:
  completions: 1
  parallelism: 1
  template:
    metadata:
      labels:
        app: batch-task
    spec:
      containers:
        - name: batch
          image: busybox:latest
          command: ["sh", "-c", "echo Hello dosto && sleep 10"]
      restartPolicy: Never
```

**Explanation:**
- `kind: Job`, `apiVersion: batch/v1` → Jobs use the `batch/v1` API group (since they're about batch-style task processing, not always-on services).
- `spec.completions: 1` → how many times this task needs to successfully finish (1 = run once).
- `spec.parallelism: 1` → how many pods run **at the same time**. Set this higher (e.g. 3) if you want the task split across multiple pods running simultaneously.
- `template` → the pod blueprint for this job (same idea as Deployment's template).
- `image: busybox:latest` → **BusyBox** is a very small container image whose whole purpose is running simple shell commands (unlike nginx, which serves websites, or MySQL, which runs a database).
- `command: ["sh", "-c", "echo Hello dosto && sleep 10"]` → the actual task: print a message, then wait 10 seconds, then the container exits (job is "done").
- `restartPolicy: Never` → **required field for Jobs** — tells Kubernetes "once this task finishes (or fails), do NOT restart the container." (The other valid option is `OnFailure`.) Regular Deployments don't need this field, but Jobs do.

## Commands

### 1. Apply the job
```bash
kubectl apply -f job.yaml
```
Creates the job.

### 2. Check status
```bash
kubectl get pods -n nginx
```
**What you'll see over time:** `ContainerCreating` → `Running` (for ~10 seconds, since that's our sleep time) → **`Completed`**. This "Completed" status is unique to Jobs — regular app pods normally show "Running" forever.

### 3. View the pod's printed output
```bash
kubectl logs <pod-name> -n nginx
```
**What it does:** Shows the console output (stdout/stderr) from inside the container — here it would print `Hello dosto`, confirming the task actually ran.

### 4. Re-run the job
```bash
kubectl delete -f job.yaml
kubectl apply -f job.yaml
```
**Important lesson:** A Job cannot simply be "re-triggered" — since it's already marked `Completed`, you must **delete it and reapply** to run it again.

### 5. Clean up
```bash
kubectl delete -f job.yaml
```

## Pod lifecycle states (good for interviews!)
`ContainerCreating` → `Running` → `Terminating` → `Completed` (for Jobs), and error states like `ImagePullBackOff`, `CrashLoopBackOff` can occur along the way.

## Chapter 23: CronJobs

**What is a CronJob?** A Job that runs **on a repeating schedule** (like a Linux cron job) instead of just once — e.g. "take a backup every minute," "run a report every day at midnight."

## Understanding cron schedule syntax
A cron schedule has 5 fields:
```
*    *    *    *    *
minute hour day-of-month month day-of-week
```
- `*` means **"every"** in that position.
- `* * * * *` → run every single minute.
- `*/2 * * * *` → run every 2nd minute.

## Writing a CronJob manifest (cronjob.yaml)

```yaml
kind: CronJob
apiVersion: batch/v1
metadata:
  name: minute-backup
  namespace: nginx
spec:
  schedule: "*/2 * * * *"
  jobTemplate:
    spec:
      template:
        metadata:
          labels:
            app: minute-backup
        spec:
          containers:
            - name: minute-backup
              image: busybox:latest
              command:
                - sh
                - -c
                - |
                  echo "Backup Started"
                  mkdir -p /backups
                  mkdir -p /data
                  cp -r /data/. /backups/
                  echo "Backup Completed"
              volumeMounts:
                - name: data-volume
                  mountPath: /demo-data
                - name: backup-volume
                  mountPath: /backups
          restartPolicy: OnFailure
          volumes:
            - name: data-volume
              hostPath:
                path: /demo-data
                type: DirectoryOrCreate
            - name: backup-volume
              hostPath:
                path: /backups
                type: DirectoryOrCreate
```

**Explanation of the important/tricky parts:**
- `kind: CronJob`, `apiVersion: batch/v1` → CronJobs also use the `batch/v1` API.
- `spec.schedule: "*/2 * * * *"` → run every 2 minutes.
- `spec.jobTemplate` → **the tricky nested structure students commonly get wrong**: a CronJob's spec contains a `jobTemplate`, whose own `spec` contains the pod `template` — so the nesting goes: `CronJob.spec.jobTemplate.spec.template.spec.containers`. This is exactly the kind of structure best copied from the **official Kubernetes documentation** rather than memorized, since it's easy to misplace a field (common real errors from this session: putting `labels` outside `metadata`, or writing `spec.jobTemplate.spec.spec` by mistake — always check the exact nesting on the docs).
- `restartPolicy: OnFailure` → since this is a real, ongoing container process (not the earlier `Never` example) — **this field belongs to the container's spec inside the template, not to the CronJob's top-level spec.**
- **Multi-line shell command using `|`:** the `|` (pipe) character in YAML means "everything below this, indented, is one multi-line text block" — letting you write several shell command lines cleanly instead of cramming them all onto one line with `&&`.
- **Volumes** (introduced here, covered properly in the Storage chapter next):
  - `volumeMounts` (inside the container) → tells the container **where inside itself** to attach the shared folder.
  - `volumes` (at the pod level) → defines the actual folder(s) being shared, here using `hostPath` (a folder that exists directly on the *node's own filesystem*).
  - This is needed so that data survives / persists even though this specific container instance is temporary — data written to `/demo-data` and `/backups` really lives on the host machine, not just inside the disposable container.

## Commands

### 1. Apply the cronjob
```bash
kubectl apply -f cronjob.yaml
```
Creates it. (If you get YAML structure errors here, that's completely normal and expected while learning — read the error message carefully; it tells you exactly which field is misplaced.)

### 2. Check the cronjob's status
```bash
kubectl get cronjob -n nginx
```
**What it does:** Shows the cronjob's name, its schedule, whether it's currently `SUSPEND`ed, and when it last ran (`LAST SCHEDULE`).

### 3. Watch it create new pods automatically over time
```bash
kubectl get pods -n nginx
```
Run this repeatedly — every time the schedule interval passes, you'll see a **brand-new pod** get created automatically to run the task again, then show `Completed`.

### 4. Check the logs of one of the runs
```bash
kubectl logs <pod-name> -n nginx
```
Should print `Backup Started` then `Backup Completed`, confirming the scheduled task actually executed successfully.

### 5. Clean up
```bash
kubectl delete -f cronjob.yaml
```
Deletes the CronJob (and stops it from creating any further scheduled pods).

## Key lesson: Job vs CronJob
| | Job | CronJob |
|---|---|---|
| Runs | Once | Repeatedly, on a schedule |
| Use case | One-time task (migration, patch) | Recurring task (daily backup, nightly report) |

## Summary table

| Command | Purpose |
|---|---|
| `kubectl apply -f job.yaml` | Run a one-time task |
| `kubectl get pods -n <ns>` | Check if task Completed |
| `kubectl logs <pod> -n <ns>` | See the task's printed output |
