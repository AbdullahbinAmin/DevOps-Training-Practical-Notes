# Chapters 24–27: Storage, Persistent Volumes, StorageClasses, Persistent Volume Claims

## The problem (Chapter 24)
Pods are **temporary** — they can be deleted/recreated at any time (e.g. during a rolling update, a crash, or self-healing). Whatever data was inside that pod's container is **lost** when the pod is destroyed. So if your app writes important data, you need a way to keep ("persist") that data safely on the host machine, independent of any one pod's lifecycle.

This needs 2 things: **Persistent Volume (PV)** and **Persistent Volume Claim (PVC)**.

---

## Chapter 25: Persistent Volume (PV)

**What is a PV?** A chunk of real storage carved out from the host machine (or cloud storage, network storage, etc.) that Kubernetes now "knows about" and can offer to pods.

### Writing a PV manifest (pv.yaml)
```bash
vim pv.yaml
```
```yaml
kind: PersistentVolume
apiVersion: v1
metadata:
  name: local-pv
  namespace: nginx
  labels:
    type: local
spec:
  capacity:
    storage: 1Gi
  accessModes:
    - ReadWriteOnce
  persistentVolumeReclaimPolicy: Retain
  storageClassName: local-storage
  hostPath:
    path: /mnt/data
```

**Explanation:**
- `kind: PersistentVolume`, `apiVersion: v1` → PV uses the core `v1` API.
- `metadata.labels.type: local` → an optional tag identifying this as a "local" type of storage.
- `spec.capacity.storage: 1Gi` → how much storage this PV provides (1 gibibyte, carved out from your host's total disk, e.g. out of a 30GB EC2 volume).
- `spec.accessModes: ReadWriteOnce` → controls **how** this storage can be used: `ReadWriteOnce` means it can be mounted read-write by **one** node at a time (other options exist for shared/multi-node access, but this is the simplest and most common for a single pod).
- `spec.persistentVolumeReclaimPolicy: Retain` → what happens to the actual data when the PV is deleted. `Retain` means "keep the data safe on the host even if the PV object itself is deleted" (as opposed to `Delete`, which would wipe the data too).
- `spec.storageClassName: local-storage` → labels this PV as belonging to the `local-storage` class (see Chapter 26 below) — this is how a PVC later finds a matching PV.
- `spec.hostPath.path: /mnt/data` → **this is the key part**: the actual folder on the host machine's filesystem being used for this storage.

### Commands
```bash
kubectl apply -f pv.yaml
kubectl get pv
```
**What you'll see:** Your PV listed with capacity `1Gi`, access mode `RWO` (short for ReadWriteOnce), reclaim policy `Retain`, and status **`Available`** — meaning it's ready to be claimed by something, but nothing has claimed it yet.

## Chapter 26: StorageClasses

**What is a StorageClass?** A "category" or "type" describing *how* the storage is provisioned — e.g. `local-storage` (data lives on the same host machine as the pod), or various cloud-provider storage types (AWS EBS, Azure Disk, etc.) in real production clusters. Think of it like choosing between a hard disk, a pen drive, or a DVD — different mediums for storing data.

### Commands
```bash
kubectl get sc
```
**What it does:** `sc` = StorageClass. Lists all available storage classes in the cluster. On a KIND cluster, you'll typically see one called **`standard`** (or `local-path`) provided automatically by KIND's default local-path-provisioner — this is what actually backs the `local-storage` name used in the PV.

## Key lesson
The **StorageClass name** you use in your PV/PVC (`local-storage` in this example) must correspond to something the cluster actually understands how to provision — check `kubectl get sc` (or your cluster's/namespace's storage docs) to find the correct value if you get errors.

## Chapter 27: Persistent Volume Claim (PVC)

**What is a PVC?** A **request** for storage. A PV just sits there "available" — a Pod can't use it directly. A PVC is how a Pod (via its Deployment) "claims" a specific amount of that available storage for itself — like claiming your own water bottle out of a pile of unlabeled ones.

### Writing a PVC manifest (pvc.yaml)
```yaml
kind: PersistentVolumeClaim
apiVersion: v1
metadata:
  name: local-pvc
  namespace: nginx
spec:
  accessModes:
    - ReadWriteOnce
  resources:
    requests:
      storage: 1Gi
  storageClassName: local-storage
```

**Explanation:**
- `kind: PersistentVolumeClaim` → this file describes a request for storage, not the storage itself.
- `spec.accessModes` → must match (or be compatible with) the PV's access mode — `ReadWriteOnce` here too.
- `spec.resources.requests.storage: 1Gi` → **how much** storage this claim is asking for (out of the 1Gi the PV has available, this claim wants the full 1Gi).
- `spec.storageClassName: local-storage` → **must match the PV's storageClassName**, or the claim won't be able to find/bind to that PV.

### Commands

### 1. Apply the PVC
```bash
kubectl apply -f pvc.yaml
```

### 2. Check the PVC and PV status
```bash
kubectl get pvc -n nginx
kubectl get pv
```
**What you'll see:** The PVC shows status **`Bound`**, and the PV's status changes from `Available` to `Bound` too — confirming the claim successfully matched and "locked in" that specific PV.

**Common error to know about:** *"PersistentVolumeClaim 'local-pvc' not found"* — this usually happens because the **PV and PVC were created in different namespaces** (or one in `default`, one in your actual namespace). The namespace field on both must line up correctly.

### 3. Delete a resource with a typo/mistake and recreate it correctly
```bash
kubectl delete pvc local-pvc -n default
kubectl delete pv local-pv
```
Cleans up a wrongly-namespaced resource before reapplying the corrected version.

## Connecting it all: mounting the PVC in a Deployment

```yaml
spec:
  template:
    spec:
      containers:
        - name: nginx
          image: nginx:latest
          volumeMounts:
            - name: my-volume
              mountPath: /usr/share/nginx/html
      volumes:
        - name: my-volume
          persistentVolumeClaim:
            claimName: local-pvc
```

**Explanation:**
- `volumeMounts` (inside the container spec) → tells this specific container: "attach a volume named `my-volume` at this internal path (`/usr/share/nginx/html`, which is where nginx serves its web files from)."
- `volumes` (at the pod spec level, alongside `containers`) → defines what `my-volume` actually IS: here, it references our PVC (`claimName: local-pvc`) — this is the actual link connecting the container's mounted folder to the real persistent storage.

### Commands to inspect/debug this setup

```bash
kubectl apply -f deployment.yaml
kubectl get pods -n nginx
```
If a pod is stuck in `Pending`, debug with:
```bash
kubectl describe pod <pod-name> -n nginx
```
A common error here: **"0 out of 4 nodes are available for persistent volume 'local-pvc' not found"** — again, usually a **namespace mismatch** between the PV, PVC, and Deployment.

### Finding the actual data on the host (KIND-specific debugging trick)
Since KIND runs "worker nodes" as Docker containers (not real separate machines), to actually see the files on the "node":
```bash
kubectl get pods -n nginx -o wide
```
Note which worker node the pod is on, then find that node's actual Docker container:
```bash
docker ps
```
Then go inside that specific container (which represents the worker node):
```bash
docker exec -it <container-id> bash
```
Then, inside that container, navigate to the folder specified in your PV's `hostPath`:
```bash
ls /mnt/data
```
This confirms the data your pod writes is actually landing in the folder you defined — proving the persistent volume setup is working end-to-end.

## Key lesson for students
- **PV** = actual storage carved out and made available.
- **PVC** = a request/claim on that storage.
- **StorageClass** = the "type/category" of storage being used.
- Always double-check **namespaces match** across PV, PVC, and the Deployment using them — this is the #1 source of errors in this topic.
