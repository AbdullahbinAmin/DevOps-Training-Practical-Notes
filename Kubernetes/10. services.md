# Chapter 28: Services

**What is a Service?** A stable "front door" that redirects traffic to a group of Pods (matched via labels/selectors), so outside users (or other parts of the cluster) don't need to track individual Pod IPs — which change every time a pod is recreated.

## Writing a Service manifest (service.yaml)

```bash
vim service.yaml
```
```yaml
kind: Service
apiVersion: v1
metadata:
  name: nginx-service
  namespace: nginx
spec:
  selector:
    app: nginx
  ports:
    - port: 80
      targetPort: 80
      protocol: TCP
  type: ClusterIP
```

**Explanation:**
- `kind: Service`, `apiVersion: v1` → Services use the core `v1` API.
- `spec.selector: app: nginx` → same label-matching idea as Deployments — the Service will route traffic to **any pod** whose label matches `app: nginx`.
- `spec.ports`:
  - `port: 80` → the port the **Service itself** exposes to whoever is calling it (from outside the pod).
  - `targetPort: 80` → the port the **actual pod/container** is listening on internally (nginx listens on 80). These two don't have to match — e.g. you could expose the service on `port: 8080` while the pod listens on `targetPort: 80`.
  - `protocol: TCP` → standard connection-based network protocol.
- `spec.type` → controls **how** this service is reachable. Four common types:
  - `ClusterIP` (the **default** if you don't specify a type at all) → only reachable from *inside* the cluster, at an internal IP.
  - `NodePort` → opens a specific port (in the range 30000–32767) on **every node**, making the service reachable from outside via `<any-node-ip>:<nodeport>`.
  - `LoadBalancer` → typically used on real cloud providers (AWS/Azure/GCP) — automatically provisions an external load balancer in front of your service.
  - `ExternalName` / static external IP → lets you point a service at a fixed external address.
  - (Headless Service — no `ClusterIP` assigned at all — is typically used together with StatefulSets, covered in the next chapter.)

## Commands

### 1. Apply the service
```bash
kubectl apply -f service.yaml
```
Creates the service, linking it to any pod labeled `app: nginx`.

### 2. Try accessing it directly (and understand why it might fail)
Visiting `http://<ec2-public-ip>:80` in your browser may **not work directly**, because your whole Kubernetes cluster (KIND) is itself running **inside a Docker container** on the EC2 instance — so the EC2 instance's own port 80 isn't automatically the same as the cluster's internal port 80. You need to explicitly forward traffic.

### 3. Forward a local port to the service
```bash
sudo kubectl port-forward service/nginx-service -n nginx --address 0.0.0.0 8080:80
```
**What it does:**
- `port-forward` → temporarily creates a tunnel from a port on your host machine straight to the service (useful for quick testing/demos, not typically used in real production).
- `service/nginx-service` → which service to forward to.
- `-n nginx` → its namespace.
- `--address 0.0.0.0` → listen on **all network interfaces** of the host (not just `localhost`), which is necessary if you want to access it from your own laptop's browser using the EC2's public IP.
- `8080:80` → format is `<local-port>:<service-port>` — "map my local port 8080 to the service's port 80."

**Common errors and fixes seen in this session:**
- *"bind: address already in use"* → the port you chose (e.g. 80) is already taken by something else on the host; simply choose a different port (e.g. 81) instead.
- If you need to run with elevated permission to bind low-numbered ports (below 1024), use `sudo -E kubectl port-forward ...` (`-E` preserves your existing environment variables while running as root).

### 4. Open the new port in your AWS Security Group
Since you picked, say, port `81`, you must also go to your EC2 instance's **Security Group → Inbound Rules → Add Rule**, and allow inbound traffic on port `81` — otherwise AWS's firewall will block it even though `kubectl port-forward` is running correctly.

### 5. Access it in your browser
```
http://<ec2-public-ip>:81
```
Should now show nginx's default **"Welcome to nginx!"** page — confirming the complete flow works end-to-end.

## The complete journey (good to remember for interviews)
**Namespace → Pod (with a container inside) → Deployment (manages replicas of that pod) → Service (exposes it) → You, the user, accessing it in a browser.**
