# Chapters 33–34: ConfigMaps & Secrets

## The problem
Right now, environment variable values (like the database name) are hardcoded directly inside the big StatefulSet YAML file. If you need to change a value later, you have to dig through that whole file. It's cleaner to keep **configuration separate from the main resource definition**.

## Chapter 33: ConfigMaps

**What is a ConfigMap?** A separate object that stores plain-text configuration values (key-value pairs), which other resources (like a StatefulSet or Deployment) can then **reference** instead of hardcoding.

### Writing a ConfigMap (configmap.yaml)
```yaml
kind: ConfigMap
apiVersion: v1
metadata:
  name: mysql-config
  namespace: mysql
data:
  MYSQL_DATABASE: "deps"
```

**Explanation:**
- `kind: ConfigMap`, `apiVersion: v1` → core API.
- `data:` → where the actual key-value configuration lives — here just one key, `MYSQL_DATABASE`, with value `deps`.

### Apply it
```bash
kubectl apply -f configmap.yaml
```

### Reference the ConfigMap from the StatefulSet
Instead of:
```yaml
env:
  - name: MYSQL_DATABASE
    value: "deps"
```
you write:
```yaml
env:
  - name: MYSQL_DATABASE
    valueFrom:
      configMapKeyRef:
        name: mysql-config
        key: MYSQL_DATABASE
```
**Explanation:**
- `valueFrom` (instead of a plain `value`) → tells Kubernetes "don't take this value literally, fetch it from somewhere else."
- `configMapKeyRef` → **capital `R`** in "Ref" matters — a lowercase typo here (`configMapKeyref`) causes a decoding error. This is exactly the kind of small structural detail that's best copied from the official Kubernetes docs (search **"kubernetes configmap environment variable"**) rather than typed from memory.
- `name: mysql-config` → which ConfigMap to pull from.
- `key: MYSQL_DATABASE` → which specific key inside that ConfigMap to use.

### Reapply the updated StatefulSet
```bash
kubectl delete statefulset mysql-statefulset -n mysql
kubectl apply -f statefulset.yaml
```
**Why delete first?** Because some structural changes to a StatefulSet's `env` can't just be "updated" cleanly on top of the existing one — deleting and recreating is the reliable path while learning.

```bash
kubectl get pods -n mysql
```
Confirms the pods still come up fine, now pulling `MYSQL_DATABASE`'s value from the ConfigMap instead of a hardcoded string.

## Chapter 34: Secrets

**Problem:** `MYSQL_ROOT_PASSWORD` is sensitive — you don't want it sitting in plain, readable text inside your YAML file (or a ConfigMap, which is also plain text). For sensitive values, Kubernetes provides **Secrets**.

### Step 1: Base64-encode the value
```bash
echo -n "root" | base64
```
**What it does:** `echo -n "root"` prints the text `root` without a trailing newline; piping it into `base64` encodes it into Base64 format (e.g. produces something like `cm9vdA==`). **Important note (as explained in the video): Base64 is NOT encryption** — it's just a way of representing text as binary-safe data that computers handle more easily. Anyone can reverse it in seconds:
```bash
echo "cm9vdA==" | base64 --decode
```
This instantly gives back `root`. So Secrets in plain Kubernetes give you **convenience and separation**, not real security — for genuinely sensitive data, real projects add encryption at rest, sealed-secrets tools, or a dedicated secrets manager (like AWS Secrets Manager or HashiCorp Vault).

### Step 2: Write the Secret manifest (secret.yaml)
```yaml
kind: Secret
apiVersion: v1
metadata:
  name: mysql-secret
  namespace: mysql
data:
  MYSQL_ROOT_PASSWORD: cm9vdA==
```
**Explanation:**
- `kind: Secret` (**not** "Secrets" — a common typo) → this file describes a Secret.
- `data:` → same key-value structure as ConfigMap, **but the values here must already be Base64-encoded** (you paste in the output from step 1, not the plain text).

### Step 3: Apply it
```bash
kubectl apply -f secret.yaml
```

### Step 4: Reference the Secret from the StatefulSet
```yaml
env:
  - name: MYSQL_ROOT_PASSWORD
    valueFrom:
      secretKeyRef:
        name: mysql-secret
        key: MYSQL_ROOT_PASSWORD
```
**Explanation:** Exactly the same pattern as ConfigMap, just `secretKeyRef` instead of `configMapKeyRef`.

### Step 5: Reapply
```bash
kubectl apply -f secret.yaml
kubectl delete statefulset mysql-statefulset -n mysql
kubectl apply -f statefulset.yaml
kubectl get pods -n mysql
```

### Step 6: Confirm it still works (and that nothing is hardcoded in the YAML anymore)
```bash
kubectl exec -it mysql-statefulset-1 -n mysql -- bash
mysql -u root -p
```
(enter `root` when asked for the password)
```sql
SHOW DATABASES;
```
You should still see the `deps` database — proving the whole chain (Secret → env variable → MySQL container) worked correctly, even though the password and database name are no longer written anywhere directly in the StatefulSet file itself.

## Key lesson for students
- **ConfigMap** = for **non-sensitive** configuration (app settings, database names, feature flags).
- **Secret** = for **sensitive** values (passwords, API keys, tokens) — stored Base64-encoded, but remember: **Base64 encoding is not encryption**, it's just a computer-friendly text format. Real production security needs more (encryption at rest, RBAC restricting who can read Secrets, external secret managers).
- Both let other resources reference their values via `valueFrom` instead of hardcoding — making your main YAML files reusable and your configuration/secrets swappable independently.

## Summary table

| Command | Purpose |
|---|---|
| `kubectl apply -f configmap.yaml` | Create a ConfigMap |
| `echo -n "<value>" \| base64` | Base64-encode a value for a Secret |
| `echo "<base64-value>" \| base64 --decode` | Decode it back (proves it's not truly secure) |
| `kubectl apply -f secret.yaml` | Create a Secret |
| `kubectl delete statefulset <name> -n <ns>` + `kubectl apply -f statefulset.yaml` | Recreate after changing env references |
