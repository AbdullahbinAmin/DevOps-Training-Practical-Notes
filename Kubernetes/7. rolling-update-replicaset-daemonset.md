# Chapters 19–21: Rolling Updates, ReplicaSets, DaemonSets

## Chapter 19: Rolling Updates in a Deployment

### 1. See more detail about which node each pod is on
```bash
kubectl get pods -n nginx -o wide
```
**What it does:** The `-o wide` flag ("output: wide") adds extra columns to the output — including which **node** each pod is running on, its internal IP, etc. Without it, you only see basic info like name and status.

### 2. Update the image being used (this triggers a rolling update)
```bash
kubectl set image deployment/nginx-deployment nginx=nginx:1.27.3 -n nginx
```
**What it does:**
- `kubectl set image` → the command specifically for changing which image a running Deployment uses.
- `deployment/nginx-deployment` → which Deployment to update.
- `nginx=nginx:1.27.3` → format is `<container-name>=<new-image>:<tag>`. This says "the container named `nginx` inside this deployment should now use image `nginx` at version tag `1.27.3`" instead of whatever it was using before.
- `-n nginx` → the namespace.

**Common mistake to watch for:** the format is `<container-name>=<image>`, NOT `<image>=<container-name>`. Also, a typo in the tag (like `1.27.3` written as `1.2 7.3`) will cause an **"ImagePullBackOff"** error, since Kubernetes will try to pull an image tag that doesn't actually exist.

### 3. Watch the rolling update happen in real time
```bash
kubectl get pods -n nginx
```
Run this repeatedly (or with `--watch`) right after the `set image` command, and you'll see:
- Some old pods still `Running`.
- New pods appear as `ContainerCreating`.
- Old pods get terminated **one at a time**, replaced by new ones, until eventually all pods are running the new image.

**This is exactly what "rolling update" means** — Kubernetes never kills *all* the old pods at once. It replaces them gradually, so your application **never goes fully down** during an update — some pods are always serving traffic.

### 4. Clean up (delete the deployment)
```bash
kubectl delete -f deployment.yaml
```
**What it does:** Deletes whatever resource(s) are described in that file — here, the Deployment (which in turn removes its ReplicaSet and Pods too).

## Key lesson
A **Deployment**'s superpower over a plain ReplicaSet is exactly this: **rolling updates** — updating the image/config gradually with zero downtime, instead of destroying and recreating every pod all at once.

## Chapter 20: ReplicaSets

A **ReplicaSet** manages a fixed number of identical pod copies — but unlike a Deployment, **it cannot do rolling updates**. It's simpler and more limited.

### Writing a ReplicaSet manifest (replicaset.yaml)
Almost identical structure to a Deployment — just change `kind`:
```yaml
kind: ReplicaSet
apiVersion: apps/v1
metadata:
  name: nginx-replicaset
  namespace: nginx
spec:
  replicas: 2
  selector:
    matchLabels:
      app: nginx
  template:
    metadata:
      labels:
        app: nginx
    spec:
      containers:
        - name: nginx
          image: nginx:latest
```
**The only real differences from a Deployment YAML:**
- `kind: ReplicaSet` instead of `kind: Deployment`.
- Everything else (`selector`, `template`, `containers`) stays exactly the same structure.

### Commands
```bash
kubectl apply -f replicaset.yaml
```
Creates the ReplicaSet with the requested number of replicas (here, 2 pods, both "Ready").

```bash
kubectl delete -f replicaset.yaml
```
Deletes it.

## Key lesson
- **Deployment vs ReplicaSet:** almost the same YAML, but **Deployments support rolling updates/rollbacks**, while plain ReplicaSets don't. In real projects, you'll almost always use a Deployment rather than a bare ReplicaSet directly — Kubernetes actually creates a ReplicaSet *for you* behind the scenes whenever you make a Deployment.
- **StatefulSets** (mentioned but covered properly in the Storage chapter later) add ordered, numbered, stateful identity to each pod (pod-0, pod-1...) — used for databases.

## Chapter 21: DaemonSets

**What is a DaemonSet?** Ensures that **every single node** in your cluster gets **at least one copy** of a particular pod running on it — like community food distribution at a "bhandara" (free meal event) where everyone present gets served, no one is skipped.

Compare all four replica-controlling objects:
| Object | What it guarantees |
|---|---|
| ReplicaSet | Exactly N copies of a pod, wherever the scheduler decides to place them |
| StatefulSet | N copies, each with a stable numbered identity + persistent state |
| Deployment | N copies + rolling updates/rollbacks/auto-healing |
| **DaemonSet** | **Exactly one copy on every node** (no `replicas:` needed — automatically matches the node count) |

### Writing a DaemonSet manifest (daemonset.yaml)
Same structure as a ReplicaSet, just change `kind` and remove `replicas` (since DaemonSet doesn't use a replica count — it automatically creates one pod per node):
```yaml
kind: DaemonSet
apiVersion: apps/v1
metadata:
  name: nginx-daemonset
  namespace: nginx
spec:
  selector:
    matchLabels:
      app: nginx
  template:
    metadata:
      labels:
        app: nginx
    spec:
      containers:
        - name: nginx
          image: nginx:latest
```
**Key difference from ReplicaSet YAML:** No `replicas:` field at all — a DaemonSet automatically figures out how many pods to create (one per node), rather than you specifying a fixed number.

### Commands
```bash
kubectl apply -f daemonset.yaml
```
Creates the DaemonSet.

```bash
kubectl get pods -n nginx -o wide
```
**What you'll see:** If your cluster has 3 worker nodes, you'll see exactly 3 pods created — one per worker node (`-o wide` lets you confirm each pod landed on a *different* node).

```bash
kubectl delete -f daemonset.yaml
```
Deletes the DaemonSet (and its pods).

## Key lesson for students
- Use a **DaemonSet** when you need something running on **every node** — common real-world examples: log collectors (like Fluentd), monitoring agents (like Prometheus Node Exporter), or network plugins — things that need a presence on every single machine in the cluster, not just "some number of copies somewhere."
