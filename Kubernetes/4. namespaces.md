# Chapter 14: Namespaces

**What is a Namespace?** Think of it as a labeled folder/group inside your cluster. All resources (Pods, Deployments, Services) related to one project or team can be grouped into one namespace, kept isolated from other namespaces, which makes managing a big cluster much easier.

## Commands

### 1. List all namespaces
```bash
kubectl get namespace
```
or the shorter version:
```bash
kubectl get ns
```
**What it does:** Both commands do the exact same thing — `ns` is just the official shorthand for `namespace`. Lists all namespaces currently in the cluster. By default you'll see built-in ones like:
- `default` → where anything goes automatically if you don't specify a namespace (just like an unlabeled item ending up in a generic "misc" pile).
- `kube-system` → where Kubernetes' own internal components live (CoreDNS, etcd, API server, controller-manager, kube-proxy, scheduler, etc.)
- `kube-node-lease` → stores heartbeat/lease information about each node.
- `kube-public` → publicly readable info, accessible even without special permissions.
- `local-path-storage` → used by KIND for its default local storage class.

### 2. See what's running in the `default` namespace
```bash
kubectl get pods
```
**What it does:** Lists pods. Since no namespace was specified, it only looks in `default` — if nothing has been created there yet, it says **"No resources found in default namespace."**

### 3. See what's running in a SPECIFIC namespace
```bash
kubectl get pods -n kube-system
```
**What it does:** The `-n <namespace>` flag (short for `--namespace`) tells kubectl "look inside this specific namespace" instead of the default one. This is how you'd see all the Kubernetes system components like CoreDNS, etcd, API server, etc.

### 4. Create a new namespace (quick way, command line)
```bash
kubectl create ns nginx
```
**What it does:** Creates a brand new namespace called `nginx`. (`create ns` = "create namespace".) This is a quick throwaway way to make a namespace — but the recommended, proper way is with a YAML file (see below).

### 5. Run a quick pod (a fast way to test, similar to `docker run`)
```bash
kubectl run nginx --image=nginx
```
**What it does:** Just like `docker run nginx` starts a container from the nginx image, `kubectl run nginx --image=nginx` creates and starts a single **Pod** named `nginx`, using the `nginx` image pulled from Docker Hub.
- If you don't specify `-n <namespace>`, it always lands in `default`, **even if you meant it for a specific namespace** — a common beginner mistake!

### 6. Run a pod INTO a specific namespace
```bash
kubectl run nginx --image=nginx -n nginx
```
**What it does:** Same as above, but `-n nginx` explicitly places this new pod inside the `nginx` namespace instead of `default`.

### 7. Delete a pod
```bash
kubectl delete pod nginx -n nginx
```
**What it does:** Deletes the pod named `nginx` that lives inside the `nginx` namespace. (If you forget `-n <namespace>`, kubectl assumes `default` and won't find it if it's actually elsewhere.)

### 8. Delete a namespace
```bash
kubectl delete namespace nginx
```
**What it does:** Deletes the entire namespace named `nginx` — and everything inside it goes with it (pods, deployments, services, etc. all get removed together).

## The proper way: writing a Namespace as a YAML (manifest) file

Command-line commands are quick, but easy to forget. The recommended, "real" way in Kubernetes is to describe what you want in a **YAML manifest file**, then apply it.

### 1. Make a project folder
```bash
mkdir nginx
cd nginx
```
Creates and enters a folder to keep this app's YAML files organized.

### 2. Create the namespace YAML file
```bash
vim namespace.yaml
```
Opens vim to write the file. Example content:
```yaml
kind: Namespace
apiVersion: v1
metadata:
  name: nginx
```
**Explanation:**
- `kind: Namespace` → tells Kubernetes "this file describes a Namespace object."
- `apiVersion: v1` → the version of the Kubernetes API being used to create this (namespaces use the core `v1` API, since it's a very basic, long-stable feature).
- `metadata:` → an object holding extra descriptive info about this resource.
  - `name: nginx` → the actual name you're giving this namespace.

### 3. Apply the YAML file to the cluster
```bash
kubectl apply -f namespace.yaml
```
**What it does:** `apply -f <file>` reads your YAML file and creates (or updates, if it already exists) the resource(s) described inside it, sending the request to the cluster's API server.

> **`create` vs `apply`:** `kubectl create -f file.yaml` only works the very first time (it'll error if the resource already exists). `kubectl apply -f file.yaml` works both the first time (creates it) AND every time after (updates it if you changed the file) — so most experienced users always use `apply`.

### 4. Confirm it was created
```bash
kubectl get ns
```
You should now see your `nginx` namespace listed alongside the built-in ones.

## Key lesson for students
- **Everything in Kubernetes is a YAML manifest file.** You describe *what you want* (declarative), and Kubernetes makes it happen.
- Prefer writing YAML files + `kubectl apply -f` over typing one-off `kubectl run`/`kubectl create` commands, so your setup is documented, repeatable, and version-controllable.
