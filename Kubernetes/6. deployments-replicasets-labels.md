# Chapters 16–18: Deployments, ReplicaSet vs StatefulSet vs Deployment, Labels & Selectors

## Why do we need a Deployment?
A single Pod can crash, or get too much traffic and die. Real apps need **multiple identical copies (replicas)** of a pod running at once, so:
- If one dies, others still serve traffic.
- Traffic can be spread across many copies.

There are 3 Kubernetes objects that manage replicas, each with a different purpose:
- **ReplicaSet** → only job is keeping N identical copies of a pod running.
- **StatefulSet** → like ReplicaSet, but each pod gets a fixed, ordered identity (pod-0, pod-1, pod-2...) whose state/data is tracked reliably — used for databases and other apps where order/identity matters.
- **Deployment** → built on top of ReplicaSet, adds **rolling updates**: when you update the image/config, old pods are replaced gradually (one at a time) instead of all at once, so there's **no downtime**.

## Labels and Selectors (how a Deployment finds "its" pods)
- A **label** is a tag you stick on a pod, e.g. `app: nginx`.
- A **selector** is the rule a Deployment uses to say "manage any pod whose label matches this."
- If the pod's label and the Deployment's selector match → that pod is considered part of this Deployment and gets scaled/updated by it.

## Writing a Deployment manifest (deployment.yaml)

```bash
vim deployment.yaml
```
```yaml
kind: Deployment
apiVersion: apps/v1
metadata:
  name: nginx-deployment
  namespace: nginx
spec:
  replicas: 2
  selector:
    matchLabels:
      app: nginx
  template:
    metadata:
      labels:
        app: nginx
    spec:
      containers:
        - name: nginx
          image: nginx:latest
          ports:
            - containerPort: 80
```

**Explanation, section by section:**
- `kind: Deployment` → this file describes a Deployment.
- `apiVersion: apps/v1` → **important gotcha**: unlike Pods and Namespaces (which use `v1`), Deployments (and ReplicaSets/StatefulSets) use `apps/v1`. If you're not sure of the right value, search **"deployment kubernetes"** on Google and copy from the official docs.
- `metadata.name` / `metadata.namespace` → name and namespace of the Deployment itself.
- `spec.replicas: 2` → **how many identical pod copies** you want running at all times.
- `spec.selector.matchLabels` → the rule the Deployment uses to find which pods belong to it — here, any pod labeled `app: nginx`.
- `spec.template` → the **blueprint** for the pods this Deployment will create. Notice it looks just like a Pod's `metadata` + `spec`, nested inside.
  - `template.metadata.labels: app: nginx` → this label is stamped onto every pod created from this template — and it **must match** `spec.selector.matchLabels` above, or Kubernetes will reject the Deployment with an error.
  - `template.spec.containers` → same container definition as a normal Pod (name, image, ports).

## Commands

### 1. Apply the deployment
```bash
kubectl apply -f deployment.yaml
```
Creates the Deployment. Kubernetes will then automatically create a ReplicaSet, which in turn creates the actual Pods (2 of them, per `replicas: 2`).

### 2. Check the pods got created
```bash
kubectl get pods -n nginx
```
You should now see 2 pods running (matching `replicas: 2`).

### 3. Delete a pod manually — and watch it come back!
```bash
kubectl delete pod nginx -n nginx
```
**What it does:** Deletes one pod directly. But since a Deployment is watching and enforcing "there must always be 2 replicas," it **immediately creates a new pod** to replace the deleted one. This is the self-healing behavior Kubernetes is famous for.

### 4. Scale the deployment up or down
```bash
kubectl scale deployment nginx-deployment -n nginx --replicas=5
```
**What it does:** Changes the number of running replicas on the fly, without editing/reapplying the YAML file.
- `scale deployment <name>` → which deployment to scale.
- `-n nginx` → its namespace.
- `--replicas=5` → the new desired count. Kubernetes will immediately create 3 more pods (since it already had 2) to reach 5 total.

You can scale it back down too:
```bash
kubectl scale deployment nginx-deployment -n nginx --replicas=1
```

### 5. Check the ReplicaSets
```bash
kubectl get rs -n nginx
```
**What it does:** `rs` is short for ReplicaSet. Even though you created a Deployment, Kubernetes automatically creates a ReplicaSet underneath it to actually manage the pod count — this command shows you that ReplicaSet and how many replicas it currently has.

## Key lesson for students
- You almost never create a ReplicaSet directly by hand — you create a **Deployment**, and Kubernetes automatically creates and manages the ReplicaSet for you.
- Deployments = ReplicaSets + rolling updates (covered in the next chapter).
- Labels + Selectors are how Kubernetes objects "find" the pods they're supposed to manage — get the labels wrong, and your Deployment will create pods it doesn't recognize as its own (or worse, hijack pods it shouldn't).

| Command | Purpose |
|---|---|
| `kubectl apply -f deployment.yaml` | Create/update a Deployment |
| `kubectl get pods -n <ns>` | Check running pods |

| `kubectl scale deployment <name> -n <ns> --replicas=<N>` | Change number of replicas |
