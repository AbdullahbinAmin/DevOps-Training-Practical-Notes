# Chapters 35–37: Resource Requests/Limits, Probes, Taints & Tolerations

## Chapter 35: Resource Requests and Limits

**The problem:** A node (e.g. a t2.medium with 4GB RAM, 2 vCPUs) can run many pods. If one greedy pod (say, nginx) is allowed to consume ALL the node's memory, other pods (like MySQL) that need to run on the same node will be starved. You need to control how much of the node's resources each pod is allowed to use.

## Adding resource requests/limits to a container spec
```yaml
spec:
  containers:
    - name: nginx
      image: nginx:latest
      resources:
        requests:
          cpu: "100m"
          memory: "128Mi"
        limits:
          cpu: "200m"
          memory: "256Mi"
```

**Explanation, using the food analogy from the video:**
- `requests` → the **minimum** guaranteed amount of resources this container needs to even start running — like telling your mom "give me at least 2 rotis." The scheduler uses this number to decide which node has enough room for this pod.
  - `cpu: "100m"` → `m` = **millicores** (1000m = 1 full CPU core), so `100m` = one-tenth of a CPU core.
  - `memory: "128Mi"` → `Mi` = mebibytes (roughly megabytes), so 128 MiB of RAM requested.
- `limits` → the **maximum** this container is ever allowed to consume — like "don't give me more than 2 rotis even if I ask." If the container tries to exceed its memory limit, it gets killed/restarted (OOMKilled); CPU limits just throttle it instead.

**Common structural mistakes to avoid (both hit in this session):**
- The field is `requests` (plural, inside `resources`), **not** `request` — a decoding error about an "unknown field" is usually a simple singular/plural typo like this.
- `resources` (with requests/limits inside) belongs **inside** a specific container's spec, at the same indentation level as `image` and `ports` — **not** floating outside the `containers` list. A `volumeMounts` or `resources` block accidentally placed outside the container block is a very common indentation mistake (also seen in this session) — **use a proper code editor like VS Code with YAML linting**, which visually catches these indentation errors, rather than a plain terminal editor like vim, where it's much easier to miss.

## Commands to verify
```bash
kubectl apply -f deployment.yaml
kubectl get pods -n nginx -o wide
kubectl describe pod <pod-name> -n nginx
```
**What to look for in the describe output:** a section showing `Limits:` (cpu/memory) and `Requests:` (cpu/memory) for the container — confirming your quotas were applied.

## Key lesson
- Set **requests + limits** on every real-world container so no single pod can hog an entire node's resources and starve its neighbors.
- This same `resources:` block works identically inside Deployments, StatefulSets, or any pod template.

## Chapter 36: Probes

**What is a Probe?** A periodic health-check request Kubernetes automatically sends to your container, to confirm it's actually working — not just "running" (a process can be running but stuck/broken).

## The 3 types of probes
- **Liveness Probe** → "Is this pod still alive?" If it fails repeatedly, Kubernetes will **restart** the container.
- **Readiness Probe** → "Is this pod ready to receive traffic yet?" If it fails, Kubernetes **stops sending it traffic** (via the Service) but doesn't necessarily restart it — useful for apps that take time to warm up.
- **Startup Probe** → "Has this container finished starting up correctly?" Useful for slow-starting apps, so liveness checks don't kill it prematurely while it's still booting.

## Adding a liveness probe to a container spec
```yaml
spec:
  containers:
    - name: notes-app
      image: <your-dockerhub-username>/notes-app-k8s:latest
      ports:
        - containerPort: 8000
      livenessProbe:
        httpGet:
          path: /
          port: 8000
        initialDelaySeconds: 5
        periodSeconds: 10
```

**Explanation:**
- `livenessProbe.httpGet` → tells Kubernetes to periodically make an **HTTP GET request** to check health.
  - `path: /` → which URL path to hit.
  - `port: 8000` → which port on the container to hit (matching the app's actual listening port).
- `initialDelaySeconds: 5` → wait 5 seconds after the container starts before the first check (gives the app time to boot).
- `periodSeconds: 10` → repeat the check every 10 seconds.

If the HTTP request fails (non-2xx/3xx response, connection refused, timeout, etc.), the probe is considered **failed**, and after enough consecutive failures, Kubernetes restarts the container.

## Commands
```bash
kubectl apply -f deployment.yaml
kubectl describe pod <pod-name> -n <namespace>
```
**What to look for:** Events showing the probe's status. A real error hit in this session: **"Readiness probe failed: Get http://<pod-ip>:8000/: dial tcp ... connection refused"** — this happened because the probe was checking the pod's internal **cluster IP** (only reachable from inside the cluster network), which behaves differently depending on your cluster type (works fine on a real cloud cluster like EKS, but can be flaky in some local KIND setups depending on networking).

## Key lesson
- Probes are Kubernetes' way of **automatically detecting and recovering from a broken app**, even if the container process itself hasn't crashed. They're what makes "self-healing" actually intelligent, rather than just restarting a container blindly whenever the process dies.

## Chapter 37: Taints and Tolerations

**What is a Taint?** A "mark" placed on a **node**, telling the scheduler: "don't put pods here unless they specifically say they're okay with it."

**What is a Toleration?** A matching "permission" placed on a **pod**, saying "I'm okay running on a tainted node with this specific taint."

**Analogy from the video:** A taint is like a relative who has a bad reputation ("this guy is useless") — you normally wouldn't visit them (schedule a pod there). A toleration is like still being willing to visit that relative despite the bad reputation.

## Commands

### 1. Taint a node
```bash
kubectl taint nodes tws-cluster-worker prod=true:NoSchedule
```
**What it does:**
- `kubectl taint nodes <node-name>` → apply a taint to this specific node.
- `prod=true` → the taint's key-value pair (you can name this anything — here `prod` is meant to represent "this is a production-reserved node").
- `:NoSchedule` → the **effect** of the taint. `NoSchedule` means "don't schedule any NEW pods here unless they tolerate this taint" (existing pods already running there are unaffected).

### 2. Try to schedule a pod (it'll get stuck Pending if ALL nodes are tainted)
```bash
kubectl apply -f pod.yaml
kubectl get pods -n nginx
```
If all worker nodes (and the control-plane, which is **always tainted by default** to prevent normal workloads running there) are tainted, the pod stays `Pending`.

### 3. Debug why it's Pending
```bash
kubectl describe pod <pod-name> -n nginx
```
**What you'll see:** *"0/4 nodes are available: 1 node had untolerated taint {node-role.kubernetes.io/control-plane}, 3 nodes had untolerated taint {prod: true}."* — this tells you exactly which taints are blocking scheduling.

### 4. Remove a taint from a node
```bash
kubectl taint nodes tws-cluster-worker2 prod=true:NoSchedule-
```
**What it does:** Adding a trailing **`-`** (minus sign) after the taint definition **removes** that taint from the node. Now that node can accept new pods again.

```bash
kubectl get pods -n nginx
```
Once one node is untainted, a pending pod gets scheduled there automatically (proving the scheduler was just waiting for an eligible node).

### 5. Add a toleration to a pod (to let it run on a tainted node anyway)
```yaml
spec:
  tolerations:
    - key: "prod"
      operator: "Equal"
      value: "true"
      effect: "NoSchedule"
  containers:
    - name: nginx
      image: nginx:latest
```
**Explanation:**
- `tolerations` → a list at the **pod spec level** (a sibling of `containers`, not inside them).
- `key: "prod"`, `value: "true"`, `operator: "Equal"` → must **exactly match** the taint you applied (`prod=true`).
- `effect: "NoSchedule"` → must match the taint's effect too.

This says: "this pod is specifically okay running on any node tainted with `prod=true:NoSchedule`."

```bash
kubectl apply -f pod.yaml
kubectl get pods -n nginx
```
Now the pod schedules and runs successfully — even on a tainted node — because it explicitly tolerates that specific taint.

## Key lesson: Note this important detail
**A taint being removed later does NOT affect already-running pods** — once a pod is successfully scheduled on a node (whether the node was tainted-then-untainted, or the pod tolerated the taint), re-tainting that node afterward won't kick out pods already running there. Taints only affect **new scheduling decisions**, not existing pods.

## Summary table

| Command | Purpose |
|---|---|
| `kubectl taint nodes <node> <key>=<value>:NoSchedule` | Mark a node as restricted |
| `kubectl taint nodes <node> <key>=<value>:NoSchedule-` | Remove a taint (note the trailing `-`) |
| `kubectl describe pod <pod> -n <ns>` | See exactly why scheduling failed |
| Add `tolerations:` in pod spec | Allow a specific pod onto a tainted node |
