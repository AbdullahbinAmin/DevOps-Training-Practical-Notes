# Day 01 — What is Terraform?

> Terraform is an open-source Infrastructure as Code (IaC) tool: you describe your infrastructure in simple configuration files and Terraform creates and manages it for you.

## Learning Objectives
- Explain what Infrastructure as Code (IaC) means in plain English.
- Describe the problems with manual (click-in-console) infrastructure and how IaC solves them.
- Walk through Terraform's high-level workflow: write → init → plan → apply.
- Identify what the Terraform state file is and why it matters.
- Recognise that Terraform is provider-agnostic (AWS, Azure, GCP, Docker, Kubernetes, VMware).

## Prerequisites
- Basic comfort with a terminal (Command Prompt, PowerShell, or bash).
- A general idea of what a cloud VM is (for example an AWS EC2 instance).
- No installation needed yet — this note is concepts only.

## Concept

Infrastructure as Code means you stop clicking around in a web console and instead **write down** what you want. Terraform reads those files and makes reality match them.

Example: you want an EC2 instance on AWS.

```
You define (in config)              Terraform creates
------------------------            -----------------------
- Resource type (aws_instance)      ->  terraform apply  ->  EC2 instance (running) on AWS
- OS / AMI
- Instance type
- Security group
- etc...
```

### Why use IaC?

| Manual way — problems | What IaC (Terraform) gives you |
|---|---|
| Repetitive clicking | Reusable configurations |
| Inconsistency (settings differ per person) | Safe, consistent, repeatable builds |
| Hard to share or collaborate | Files live in git; teams review changes |
| No proper tracking of what exists | State management (Terraform tracks real infra) |
| Takes more time | Less human error, faster delivery |

### How Terraform works (high-level flow)

```
1. Requirement      2. Write            3. terraform plan   4. terraform apply   5. Infrastructure
   Gathering    ->     Configuration ->    Preview        ->   Terraform        ->   Ready
   Decide what        Define infra in      changes before      creates/updates      Your infra is
   you need           .tf files            applying            resources            ready to use
```

Terraform is **provider-agnostic** — the same tool and the same language (HCL, HashiCorp Configuration Language) work across multiple cloud platforms.

### Terraform — key steps

| # | Step | What it means |
|---|---|---|
| 1 | Scope & identification | Decide what you want to build |
| 2 | Choose provider(s) | AWS / Azure / GCP / others |
| 3 | Write configuration | Human-readable `.tf` files (HCL) |
| 4 | Initialize & plan | `terraform init`, `terraform plan` |
| 5 | Apply | `terraform apply` creates/updates resources |
| 6 | Track state | Terraform keeps a state file to track real infra |
| 7 | Collaboration | Work as a team (remote state, Terraform Cloud/Enterprise) |
| 8 | Manage & destroy | Update, version, destroy when no longer needed |

## Step-by-Step Practical

This is a read-only walkthrough so you can see the shape of a Terraform project. You will actually run these commands on Day 02+ once Terraform and AWS CLI are installed.

1. Create a project folder for the course.

```bash
mkdir -p ~/TF-AWS && cd ~/TF-AWS
```

2. Look at what a minimal Terraform configuration looks like (`main.tf`). Read it — do not run it yet.

```hcl
terraform {
  required_version = ">= 1.6.0"

  required_providers {
    aws = {
      source  = "hashicorp/aws"
      version = "~> 5.0"
    }
  }
}

provider "aws" {
  region = "ap-south-1"
}

resource "aws_instance" "demo" {
  ami           = "ami-0abcdef1234567890" # replace with a valid AMI for your region
  instance_type = "t3.micro"

  tags = {
    Name = "terraform-demo"
  }
}
```

3. Understand the four commands you will use constantly.

```bash
terraform init      # download the provider plugins, prepare the working directory
terraform validate  # check the syntax of your .tf files
terraform plan      # preview: what will be created, changed, destroyed
terraform apply     # make it real
```

4. And the one that tears it all down again.

```bash
terraform destroy
```

5. Note the files Terraform generates so you know what must never be committed to git.

```bash
# generated by Terraform — do NOT commit these
.terraform/            # downloaded provider plugins
terraform.tfstate      # real infrastructure state, may contain secrets
terraform.tfstate.backup
*.tfvars               # often holds sensitive values
```

## Expected Output

A `terraform plan` for the config above reads roughly like this:

```
Terraform will perform the following actions:

  # aws_instance.demo will be created
  + resource "aws_instance" "demo" {
      + ami           = "ami-0abcdef1234567890"
      + instance_type = "t3.micro"
      + id            = (known after apply)
      + public_ip     = (known after apply)
      + tags          = {
          + "Name" = "terraform-demo"
        }
    }

Plan: 1 to add, 0 to change, 0 to destroy.
```

```bash

```

## Common Errors & Fixes

| Error | Cause | Fix |
|---|---|---|
| `Error: Inconsistent dependency lock file` | Provider versions changed after `init` | Run `terraform init -upgrade` |
| `Error: No configuration files` | You ran Terraform in a folder with no `.tf` files | `cd` into your project folder |
| `Error: Invalid AMI ID` | AMI IDs are region-specific | Pick an AMI valid for your configured region |
| Second `apply` unexpectedly rebuilds a resource | You changed an immutable attribute (e.g. AMI) | Read the plan output; `~` means update, `-/+` means replace |
| Secrets leaked in a repo | `terraform.tfstate` or `.env` was committed | Add them to `.gitignore` before your first commit; rotate the exposed keys |

## Key Takeaways
- Terraform is declarative: you describe the desired end state, not the steps.
- The core loop is write → `init` → `plan` → `apply`, and `destroy` to clean up.
- State is what makes Terraform safe and repeatable — protect it and never commit it.
- One tool, many providers: skills transfer across AWS, Azure, GCP, Kubernetes, and more.
- Infrastructure as Code makes your infra reliable, reusable, and easy to manage. Practice → Build → Automate → Scale.
